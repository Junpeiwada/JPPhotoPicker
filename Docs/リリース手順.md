# リリース手順

JPPhotoPicker を GitHub Release で配布する（Developer ID 署名・公証・Sparkle 自動更新）ための手順書。仕組みは JPScreenShot と同じ。

コード側（`release.yml` / Sparkle の組み込み / `ExportOptions.plist` / ランディングページ / `Tools/release.sh`）は実装済み。ここには、**一度だけ行うセットアップ**と**毎回のリリース手順**を書く。

前提: Apple Developer Program（有料）に加入していること。

## 1. 一度だけ行うセットアップ

### 1-1. Sparkle 署名鍵

Sparkle は appcast（更新情報）を EdDSA 署名で検証する。公開鍵をアプリに埋め込み、秘密鍵で CI が署名する。

秘密鍵はこの Mac のログインキーチェーンに **アカウント名 `JPPhotoPicker`** で入っている。JPScreenShot・JPPhotoTools の鍵とは分けてある（片方が漏れても、もう片方に影響しないように）。

`generate_keys` は Sparkle の配布物にある。SPM で取得済みなら DerivedData の中にある。

```sh
B=$(ls -d ~/Library/Developer/Xcode/DerivedData/JPPhotoPicker-*/SourcePackages/artifacts/sparkle/Sparkle/bin | head -1)

$B/generate_keys --account JPPhotoPicker -p        # 公開鍵を確認する
$B/generate_keys --account JPPhotoPicker -x k.txt  # CI 登録用に秘密鍵を書き出す
```

公開鍵を変えたときは [project.yml](../project.yml) の `SUPublicEDKey` を直し、`xcodegen generate` で `JPPhotoPicker-Info.plist` を作り直して両方をコミットする。

> ⚠️ 書き出した秘密鍵のファイルは**コミットしない**（`.gitignore` 済み）。Secret に登録したら削除する。原本はキーチェーンに残る。
>
> ⚠️ `SUPublicEDKey` が正しい鍵でないと、Sparkle は起動時に「The updater failed to start」を出して動かない。

### 1-2. Developer ID 証明書

Mac App Store の外で配布するには **Developer ID Application** 証明書が要る。チーム単位の証明書なので、JPScreenShot と同じものを使う。実物は `~/Dropbox/アプリ/JPScreenShot/証明書.p12`（パスワードは同じフォルダの `パスワード.txt`）。

### 1-3. 公証用 App Store Connect API キー

`notarytool` は API キーで認証する。チーム単位なので JPScreenShot と同じキーを使う。実物は `~/Dropbox/アプリ/JPScreenShot/AuthKey_5NFM2RND38.p8`（Key ID は `キーID.txt`、Issuer ID は `IssuerID.txt`）。

`.p8` は**ダウンロードが一度きり**。失くしたら作り直しになる。

### 1-4. GitHub Secrets

**Settings → Secrets and variables → Actions** に登録する。値はファイルから `gh secret set` にパイプで渡すと、画面に出さずに済む。

| Secret 名 | 中身 |
|---|---|
| `TEAM_ID` | `L897K2C26B` |
| `DEVELOPER_ID_CERT_P12` | `.p12` の Base64 |
| `DEVELOPER_ID_CERT_PASSWORD` | `.p12` のパスワード |
| `ASC_API_KEY_P8` | `.p8` の Base64 |
| `ASC_KEY_ID` | Key ID |
| `ASC_ISSUER_ID` | Issuer ID（UUID） |
| `SPARKLE_PRIVATE_KEY` | Sparkle の秘密鍵（1-1 で書き出したもの） |

```sh
base64 -i 証明書.p12 | tr -d '\n' | gh secret set DEVELOPER_ID_CERT_P12 -R Junpeiwada/JPPhotoPicker
gh secret list -R Junpeiwada/JPPhotoPicker   # 7件あることを確認する
```

`GITHUB_TOKEN` は GitHub が自動で発行するので登録不要。`release.yml` の `permissions: contents: write` で Release の作成と gh-pages への push ができる。

### 1-5. GitHub Pages を有効にする

初回リリースで `gh-pages` ブランチができたら、**Settings → Pages** で `Deploy from a branch` / `gh-pages` / `/(root)` を選ぶ。

```sh
gh api -X POST repos/Junpeiwada/JPPhotoPicker/pages -f "source[branch]=gh-pages" -f "source[path]=/"
```

公開されると、次の2つが見えるようになる。

- ランディングページ: <https://junpeiwada.github.io/JPPhotoPicker/>
- appcast: <https://junpeiwada.github.io/JPPhotoPicker/appcast.xml>（アプリの `SUFeedURL`）

## 2. リリースを出す（毎回）

`Tools/release.sh` が、バージョンの更新・コミット・タグ・push までをまとめて行う。push されたタグで CI が動く。

```sh
Tools/release.sh 0.1.2        # 確認してから実行
Tools/release.sh 0.1.2 -y     # 確認なし
Tools/release.sh              # 端末なら、次の番号を提案して尋ねる
```

VSCode からは、エクスプローラーの **NPM SCRIPTS → release** を押すと、ターミナルで `Tools/release.sh` が引数なしで起動する（`package.json`）。番号の提案と発火の確認が出るので、そこで答える。

作業ツリーに未コミットの変更がある、または同じ版がすでにある（project.yml・ローカルのタグ・リモートのタグのどれか）ときは中断する。

### 出したあとの確認

- Actions の Release ワークフローが通ったか（公証の待ちで 5〜15 分かかる）
- Releases に `JPPhotoPicker-<版>.zip` が付いているか
- appcast が新しい版を指しているか: `curl -s https://junpeiwada.github.io/JPPhotoPicker/appcast.xml | grep shortVersionString`
- 前の版のアプリで「アップデートを確認…」を押すと、新しい版が見つかるか
- 落とした `.app` を初めて開いたときに Gatekeeper の警告が出ないか

## 3. バージョン番号の運用

- 表示用の `MARKETING_VERSION` は**タグの値**を CI が使う。`project.yml` の値は手元のビルドの既定値で、`Tools/release.sh` が合わせて書き換える
- タグは必ず `v` を付ける（`v0.1.2`）
- Sparkle が新旧の比較に使う `CFBundleVersion` は、CI の **run 番号**（単調に増える）を自動で使う。手で管理しない
- 初回は `0.1.1`。`project.yml` が最初から 0.1.0 なので、0.1.0 は重複として弾かれる

## 4. CI が何をしているか

[.github/workflows/release.yml](../.github/workflows/release.yml) の流れ。ランナーは `macos-26`（macOS 26 SDK が要るため）。

1. タグから版を、run 番号からビルド番号を決める
2. `swift test` で JPPhotoPickerCore のテストを流す（実画像サンプルが無いテストは skip）
3. `xcodegen generate` でプロジェクトを作る（`.xcodeproj` は git 管理外）
4. `SUPublicEDKey` が仮の値のままでないか確かめる
5. Developer ID 証明書を一時キーチェーンに入れる
6. `xcodebuild archive`（Release、Developer ID で署名）→ `-exportArchive`（Sparkle.framework も署名し直す）
7. `notarytool submit --wait` で公証し、`stapler staple` で結果を `.app` に付ける
8. zip を作って **GitHub Release** を作る（リリースノートは自動生成）
9. `generate_appcast` で `appcast.xml` を作って秘密鍵で署名する
10. `appcast.xml` と `site/` を **gh-pages** に出す

## 5. つまずきやすい点

### Info.plist は生成物だが版管理している

Sparkle の `SUFeedURL` / `SUPublicEDKey` は `INFOPLIST_KEY_*` では入れられないので、Info.plist を XcodeGen に作らせている。**正本は [project.yml](../project.yml)**。`JPPhotoPicker-Info.plist` を直接直しても、次の `xcodegen generate` で消える。

### DEBUG ビルドは自動で更新を確認しない

開発中のビルドが配布版に置き換わらないよう、DEBUG では起動時・定期の確認を止めている（`UpdaterController` のデリゲート）。メニューから手動で確認したときだけ動く。

### 適用・取り消しの実行中は、更新後の再起動を待たせる

ファイルの移動が途中で止まらないよう、Sparkle の再起動は処理が終わるまで待たせる。

### 公証は数分かかる

`notarytool submit --wait` は Apple の処理が終わるまで待つ。普段は 1〜5 分、混んでいるとそれ以上。

### 証明書の期限

Developer ID 証明書は **2027-02-01** に切れる。更新したら `.p12` を書き出し直して `DEVELOPER_ID_CERT_P12` / `DEVELOPER_ID_CERT_PASSWORD` を登録し直す。
